🔄 EVOLUCIÓN RESPECTO A LA ENTREGA PREVIA (EP2)

Del Acoplamiento Sincrónico a la Mensajería Distribuida

En EP2 consolidamos la identidad con Azure Entra ID y el API Gateway. En esta etapa (EP3/EP4), el foco exclusivo es eliminar el bloqueo HTTP y garantizar resiliencia absoluta.

⚠️ Arquitectura Previa (Sincrónica / HTTP Bloqueante)
  • Bloqueo de Hilos Web: Cada reserva obligaba al backend a esperar la notificación y auditoría antes de responder al estudiante.
  • Efecto Cascada ante Caídas: Si el servicio de correo o reportes fallaba, toda la transacción de reserva se cancelaba.
  • Pérdida de Mensajes en Errores: Sin mecanismo de reintento, los fallos transitorios destruían la trazabilidad del evento.
  • Monocopia sin Tolerancia a Fallos: El broker operaba en una sola instancia sin clustering.
🚀 Nueva Arquitectura Asíncrona (Cloud Native EP3/EP4)
  • Respuesta Inmediata: La reserva se persiste y se publica el evento en microsegundos; el usuario no espera tareas secundarias.
  • Desacoplamiento Absoluto: Productores y consumidores no se conocen; operan mediante contratos AMQP tipificados.
  • Garantía At-Least-Once: Los mensajes solo se borran tras channel.basicAck() una vez ejecutada la lógica.
  • Aislamiento en DLQs: Las cargas maliciosas o corruptas se desvían a Dead Letter sin detener a los demás mensajes.
BENEFICIO OPERACIONAL: Rendimiento x5 en picos de matrícula · Tolerancia a fallos certificada

🐇 INFRAESTRUCTURA Y TOPOLOGÍA AMQP

Clúster de 2 Nodos y Enrutamiento Inteligente

Dos nodos orquestados en Docker Compose con alta disponibilidad, balances de carga y tipología Direct & Topic.

Direct Exchange (1 a 1)

Enrutamiento determinístico con clave exacta routing.notifications hacia tareas transaccionales.

Topic Exchange (Wildcards)

Permite enrutamiento jerárquico con comodines (#) hacia múltiples consumidores independientes.

Alta Disponibilidad (HA)

Esquema sincronizado en ambos nodos. Si un nodo cae, los productores continúan operando en el segundo nodo.

🛡️ GARANTÍA DE ENTREGA Y TOLERANCIA A FALLOS

Manejo de Confirmación: ACK Manual vs Derivación a DLQ

Configuración en AcknowledgeMode.MANUAL. Explicación del ciclo de vida ante procesamiento exitoso y ante excepciones no controladas.

✅ Flujo Exitoso: Confirmación Explícita (ACK)

1. Llega el mensaje al consumidor funcional:

@RabbitListener(queues = "${campuslab.rabbitmq.queues.notifications}")
public void process(String msg, Channel ch, @Header(...) long tag) {
    try {
        // Lógica de negocio (notificación, guardado)
        ch.basicAck(tag, false); // Confirmación exitosa
    } ...
}
  • • RabbitMQ retiene el mensaje en el broker hasta que la lógica finaliza con éxito.
  • • Se evita pérdida de datos si el proceso falla a mitad de la ejecución.
  • • Una vez recibido el ACK, el broker descarta el mensaje de la memoria de forma segura.
🚨 Flujo de Fallo: Rechazo Controlado a DLQ (NACK)

2. Ante error imprevisto o carga corrupta:

} catch (Exception e) {
    log.error("Fallo detectado: {}. Enviando a DLQ", e.getMessage());
    // requeue = false para transferir automáticamente a DLQ
    ch.basicNack(tag, false, false);
}
  • • requeue=false impide el bucle infinito de reintentos venenosos (Poison Message).
  • • RabbitMQ lee los argumentos x-dead-letter-exchange de la cola.
  • • El mensaje defectuoso es transferido intacto a la cola .dlq para análisis forense.
PRUEBA DE LABORATORIO: Al enviar un mensaje con la palabra "error", el sistema ejecuta NACK y lo deposita en la DLQ en < 50ms.

⚙️ INFRAESTRUCTURA DECLARATIVA POR API REST

Microservicio Administrador de RabbitMQ

Desacoplamiento total entre infraestructura y controladores. Gestión declarativa con DTOs validados y lógica encapsulada en RabbitAdminService.

1. Endpoints REST Limpios
  • POST /api/admin/queues
    Declaración dinámica de colas.
  • DELETE /api/admin/queues/{name}
    Eliminación segura con confirmación booleana.
  • POST /api/admin/exchanges
    Creación de Direct, Topic o Fanout.
  • POST /api/admin/bindings
    Enlace dinámico de cola y exchange.
2. Encapsulación de Servicio

RabbitAdminService.java

El controlador REST desconoce por completo las clases internas de AMQP (RabbitAdmin, ConnectionFactory). Toda la gestión se expone en métodos limpios de alto nivel:

public void createQueue(String name, boolean durable)
public boolean deleteQueue(String name)
public void createExchange(String name, String type)
public void createBinding(String q, String ex, String key)
3. Validación Estricta (DTOs)

QueueDto.java / ExchangeDto.java

  • • @NotBlank: Impide nombres nulos o vacíos.
  • • @Size(min=3, max=255): Longitud controlada.
  • • @Pattern(regex="^[a-zA-Z0-9._-]+$"): Bloquea inyecciones o caracteres inválidos en el broker.
  • • @Pattern(regexp="^(direct|topic|fanout)$"): Valida tipos de exchange soportados.
